# 任务三：开源语音识别调研与实现

## 研究目标
本次作业的目标是选取可在本地环境运行的开源语音识别方案，并完成“音频文件识别 + 麦克风实时识别”的演示。要求对比多个开源方案在许可证、语言支持、流式能力、部署难度与本地适配性等维度上的差异，最终给出合理选型，并说明本地实现的目录结构与运行方式。

## 候选方案概述
本次对比的三种方案分别是：
1. `OpenAI Whisper`
2. `Vosk`
3. `FunASR`

它们都能完成语音到文本的任务，但在部署方式、资源需求与实时能力上存在明显差异。

## 方案对比分析
下面从多个维度对三种方案进行横向对比（基于常见使用与官方/社区资料的公开信息）：

| 方案 | 开源许可证 | 支持语言或方言情况 | 是否支持流式/实时识别 | 模型体量、资源占用或部署特点 | 依赖与部署难度 | 是否适合在笔记本/PC 上本地运行 | 典型适用场景 |
|---|---|---|---|---|---|---|---|
| OpenAI Whisper | MIT（模型与代码开源） | 覆盖多语言，通常可直接适配中文 | 一般以批处理为主；流式能力需额外工程实现 | 模型体量相对较大，推理依赖较强（CPU 可用但速度取决于模型规模） | 依赖 PyTorch 等；部署门槛中等偏高 | 中等（低端 CPU 可能较慢） | 离线转写、字幕生成、高质量识别 |
| Vosk | Apache-2.0（开源） | 支持多语言模型；中文模型常见且易用 | 支持基于音频流的实时识别（可边采集边输出） | 模型相对轻量，可离线加载；CPU 友好 | 依赖少，Python/C++ 接口成熟 | 是（更偏“本地部署”） | 本地转写、实时字幕、课堂/演示用例 |
| FunASR | Apache-2.0（常见组件许可，具体以项目为准） | 面向多语种 ASR；中文能力较强 | 是否“原生流式”取决于具体模式/模型与工程封装 | 工程与模型规模差异较大；部分方案对算力有要求 | 依赖与环境配置相对复杂（ASR pipeline 较多） | 中等偏难（需更完善环境） | 研究/工程化集成、较复杂的语音处理链路 |

对比可以发现：如果作业强调“本地演示可运行、能实时识别、对 CPU 资源友好”，则更需要选择部署简单且运行轻量的方案。Whisper 往往适合离线高质量转写；FunASR 更偏工程化/研究性集成；Vosk 在轻量化与实时演示方面更符合课程作业的落地需求。

## 选型理由
最终选择 `Vosk` 作为本地实现方案，原因如下：
1. 可离线运行：下载模型后即可离线加载，不依赖外部 API。
2. 对 CPU 环境友好：Vosk 的模型规模与推理流程相对轻量，适合笔记本/普通 PC 环境的演示。
3. 支持音频文件识别：对 wav/pcm 音频流解码即可输出识别文本，便于完成“文件识别”任务。
4. 支持麦克风实时识别：配合音频采集输入流，可实现边采集边解码输出中间结果与最终结果，便于完成“实时识别”任务。
5. 更适合作业演示与本地部署：脚本通过命令行即可运行，能够清晰展示本地部署方案的可复现性。

## 本地实现方案
本地实现使用仓库下的 `asr_demo/` 目录完成演示，核心由两段脚本构成：
- `recognize_file.py`：读取指定 `test.wav` 并输出最终识别文本。
- `recognize_mic.py`：调用麦克风输入，实时输出中间识别与最终识别结果。

### 目录结构
建议的目录组织如下（与本次作业说明保持一致）：
```text
HW04/
  asr_demo/
    requirements.txt
    recognize_file.py
    recognize_mic.py
    models/
      vosk-model/   # 你需要自行下载并放置的 Vosk 模型目录
```

### requirements.txt 的作用
`asr_demo/requirements.txt` 用于声明本地演示所需的最小依赖：
- `vosk`：提供语音识别模型与解码接口
- `sounddevice`：用于麦克风采集与实时音频输入

安装依赖后即可运行对应脚本。

### recognize_file.py 的功能
该脚本完成“音频文件识别”：
1. 校验模型目录是否存在（默认 `models/vosk-model`）。
2. 校验 wav 文件是否存在，并对 wav 做基本格式检查（单声道、16-bit PCM）。
3. 读取音频帧并逐块送入 Vosk 解码器，最终解析 `FinalResult()` 输出识别文本。

### recognize_mic.py 的功能
该脚本完成“麦克风实时识别”：
1. 校验模型目录是否存在（默认 `models/vosk-model`）。
2. 使用 `sounddevice` 打开麦克风输入流（默认 16kHz、单声道、int16）。
3. 在实时流中不断调用 Vosk 解码器，输出：
   - 中间识别结果（Partial）
   - 最终识别结果（Result）

### 模型目录 `models/vosk-model`
请把你下载的 Vosk 模型解压后放到：
`HW04/asr_demo/models/vosk-model/`

脚本默认会从该目录加载模型（你在 `asr_demo` 目录下运行时路径保持一致）。

### 运行前准备事项
1. 准备好 `HW04/asr_demo/models/vosk-model/`（包含 Vosk 模型所需文件与子目录）。
2. 准备测试音频文件 `test.wav`，并确保为单声道、16-bit PCM 的 WAV；若不满足，脚本会在启动阶段进行格式校验并直接报错提示。
3. 确认系统麦克风可用，并允许该终端/程序访问麦克风权限（用于实时识别）。

## 运行步骤
1. 打开终端，进入 `HW04/asr_demo`：
   - `cd HW04/asr_demo`
2. 安装依赖：
   - `pip install -r requirements.txt`
3. 运行音频文件识别（示例命令）：
   - `python recognize_file.py test.wav`
4. 运行麦克风实时识别（示例命令）：
   - `python recognize_mic.py`

### 预期输出效果
- `recognize_file.py test.wav`：终端会打印最终识别出来的文本（来自 `FinalResult()` 的 `text` 字段）；若识别结果为空，仍会打印 `final_result` 便于排查。
- `recognize_mic.py`：终端会持续输出：
  - 中间识别结果（`[中间] ...`，基于 `PartialResult()`，会随语音更新）
  - 最终识别结果（`[最终] ...`，基于 `Result()`，句段解码完成后输出）

## 实验结果与分析
本次实验以 `test.wav` 为测试文件完成了本地文件识别的验证，整体流程已成功跑通。具体表现如下：

1. 文件识别流程已成功运行：在 `HW04/asr_demo` 目录下执行 `python recognize_file.py test.wav` 后，脚本能够正常启动并完成识别流程。
2. 模型可以正常加载：模型目录 `models/vosk-model` 可被脚本正确定位与加载，未出现模型缺失或加载失败的报错。
3. 测试音频可被程序读取：`test.wav` 可被程序正常打开与读取，说明文件路径与读取逻辑工作正常（若音频格式不符合要求，脚本会在检查阶段提示并退出）。
4. 当前识别结果与原语音差异较大：本次实验虽然获得了可输出的识别文本，但与原始语音内容偏差明显，暂未达到理想的转写准确率。
5. 初步原因分析：综合现象判断，主要原因可能为模型语言与测试音频语言不匹配，或测试音频与当前模型的适配性不足（如口音、语速、录音质量等因素）。

结论：本地实现已完成，后续可通过替换更匹配的模型进一步优化识别准确率。

## 结论
综合许可证开放性、部署难度、实时识别能力与本地 PC 可运行性，本次作业选择 `Vosk` 作为本地实现方案。该方案具备离线运行、CPU 友好、支持音频文件与麦克风实时识别等特点，更符合课程演示与工程落地的需求。
